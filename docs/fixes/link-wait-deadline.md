# 取链等待窗口：按墙钟 90 秒并容忍瞬时错误

## 现象

2026-11-15 10:42 的一批自动注册（10 个流程）里，`b5db4edb` 在 10:42:37 进入
"等待邮箱验证"，10:42:38 第一次 `reg_fetch_link` 就以
`M365 请求失败：https://graph.microsoft.com/… : Net…` 失败，此后 68 秒内
**没有再发起任何查询**；10:43:46 才靠用户手动粘贴拿到链接。同批另外 9 个流程
都在 7–11 秒内自动取到，所以问题只在"取链失败"时暴露。

工作日志位置：`%LOCALAPPDATA%\com.zpool.app\logs\oauth.log`（应用内"工作日志"
面板读的就是它）。日志里 `link-fetch` 行数 = 真实查询次数，可直接判断轮询停了没有。

## 根因

1. **一次瞬时失败就丢掉整个窗口。** `autoFetchLink` 的 `catch` 里除凭据失效外
   一律 `break`，随即 `startManualLink()` 弹手动粘贴框。网络抖动、Graph 502/503、
   单次超时都会命中这条路。2026-11-13 18:27–18:32 的 Graph 抖动（3 次 502/503 +
   2 次 `Net`）已经连续踩了 5 次。
2. **90 秒是名义值，不是墙钟。** 常量是 `30 次 × 3 秒`，但每轮还有一次 Graph
   往返（日志实测约 2 秒），跑满要 ~150 秒；界面"已等 {a} 秒"用的是
   `(i+1) × 3000`，和真实耗时也对不上。
3. **单轮最长能吃掉 25 秒。** `m365.rs` 的 ureq 超时是 25s，一轮卡住就占掉窗口
   的四分之一，而且失败后同一轮不再重试。

## 修复设计

1. **按墙钟收口。** `LINK_WAIT_MS = 90_000` 作为真实截止时间；每轮用剩余预算
   判断是否还值得发起查询（`LINK_MIN_ROUND_MS = 5000`）。单次查询由
   `linkQuery()` 与剩余时间赛跑，Graph 的 25s 超时不会再让窗口拖过截止点。
2. **错误分级。** 只有凭据类错误（`invalid_grant` / `AADSTS…`）终止并跳过；
   网络 / 5xx / 超时只记一条日志（同文案去重，避免 90 秒刷屏）后继续等。
   日志改为"已等 / 还剩 / 第几次查询（含已自动重试次数）"。
3. **兜底并行。** 转手动粘贴的同时后台继续按 5 秒节奏等邮件（上限 10 分钟）：
   取到就自动 `reg_input` 下发并撤掉粘贴框，用户不必手贴；手动框新增
   「从剪贴板粘贴」，WebView 不支持剪贴板 API 时按钮自动隐藏。
4. **收口防呆。** 进入 open-link / complete-signup 等阶段、收到 result / closed、
   用户手贴之后立刻停后台轮询；`pushedLink` 去重避免同一链接下发两次。
   `clearLinkAsk()` 撤掉已经无意义的粘贴请求，让排队中的下一个流程的框顶上。
   这些收口都是必要的：驱动在 `S.answered.link` 出现时会立刻回到打开链接那一步，
   迟到的链接会把已经走到授权页的流程拽回上一阶段。

## 回归测试

新增 `scripts/tests/reg-link.test.mjs` 与 `scripts/tests/helpers/reg-link-harness.mjs`：
用 vm 执行真实 `src/reg.js`，只替换宿主 IPC、DOM 和时钟（虚拟时间），
因此测的是产品代码而不是复制出来的分支。覆盖：

- 瞬时网络错误后继续查询，下一轮取到并自动下发；
- 等待窗口按墙钟 90 秒收口（手动框出现时间在 78–95 秒之间，且之后仍有后台查询）；
- 手动框背后的兜底取到链接后自动填入并关掉弹窗；
- 凭据失效只查一次、立即终止；
- 并发批次里 A 的链接晚到时，A 的粘贴框被撤掉、B 的排队框顶上；
- 链接下发失败时保留粘贴框，同一链接不重复下发；
- 离开等邮件阶段后后台立刻收口。
